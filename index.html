Flagship case study AI & ML Backend & cloud Status: MVP

Real-Time Driver Stress & Cognitive Load Monitoring

An end-to-end machine learning MVP that classifies physiological stress vs. no stress from heart-rate-variability features (WESAD), evaluated on people the model never saw, served through a FastAPI service and a Streamlit dashboard that replays held-out recordings, with Docker and CI.

  • Repository (opens GitHub)
  • CI workflow (opens GitHub)

Problem

Can a model tell physiological stress from no stress using heart-rate-variability (HRV) features, for people it was never trained on? Driver monitoring is the target application. The labelled data available, WESAD, was recorded in a lab, so the project has to be honest about what it does and doesn’t show.

My role

Personal project, built end to end: data pipeline, feature selection, evaluation design, model, inference API, dashboard, tests, Docker setup and CI.

Approach

  1. 1 Subjects 15, 16 and 17 are held out entirely: they are the final test set and the dashboard’s replay data.
  2. 2 Leave-one-subject-out (LOSO) cross-validation runs on the remaining 12 subjects.
  3. 3 The final model is trained on all 12 training subjects and scored once on the held-out 3.

Architecture

  1. WESAD HRV CSV downloaded by script, never committed
  2. preprocessing.py schema check · dedup · labels
  3. train.py LOSO CV · held-out test
  4. joblib + metadata one pipeline artefact
  5. FastAPI /health · /model-info · /predict
  6. Streamlit replays held-out subjects

Engineering challenges

  • Label leakage hiding in the columns

    Time encodes the order of the lab protocol, and SSSQ is a self-reported stress score. Either would leak the answer, so both are excluded, along with monotonic transforms and two duplicate columns: 30 base HRV features remain.

  • Duplicated data

    One subject’s recording appears twice in the source CSV. Removing exact duplicates takes the data from 196,978 to 184,276 rows across 15 subjects.

  • Heavily overlapping windows

    HRV windows are emitted every 0.25 s. Training rows are subsampled to 1 Hz to reduce redundancy; the test set is scored on all 35,707 held-out windows.

  • People differ more than conditions do

    A random row split would put the same person in training and test and inflate every metric. Evaluation is therefore subject-independent throughout.

Model

  • scikit-learn Pipeline: median SimpleImputer → RandomForestClassifier (200 trees, max_depth 20, min_samples_leaf 5, class_weight “balanced”, fixed seed).
  • Saved as one joblib artefact, so training and inference always share preprocessing.
  • Binary target: stress = 1; baseline, amusement and meditation = 0 (22% stress). Decision threshold 0.5.
  • Most important features: MEAN_RR, HR and MEDIAN_RR.

Source: models/model_metadata.json and reports/train_log.txt in the repository (macOS run; CI on Linux reproduces within about 0.005).

Testing & deployment

  • pytest suite covering the raw-data schema, subject-independent hold-out, input validation, model output, the replay generator and every API endpoint.
  • The API returns HTTP 422 naming the problem fields for missing, unknown, non-numeric or NaN/inf input, and 503 if the model file is missing.
  • Docker image for the API; Docker Compose runs the API and the dashboard from the same image.
  • GitHub Actions on every push and pull request: install → download data (cached) → train → pytest → Docker build → smoke test of the running API container.

Outcome

  • A reproducible MVP: one command trains and evaluates, the API and dashboard run in Docker, and CI passes on main.
  • Single-window inference takes roughly 5–10 ms in-process on an Apple-silicon Mac (measured by the replay CLI).

Limitations, stated plainly

  • Lab data, not driving data: WESAD stress was induced by public speaking and mental arithmetic while seated.
  • “Cognitive load” is not modelled. The only labels are stress, baseline, amusement and meditation.
  • The dashboard replays recorded data; it is not connected to live vehicle sensors.
  • Small cohort: 15 subjects (12 for training, 3 for testing), and some people’s stress is not detected at all.
  • No per-driver calibration yet. Normalising features against each person’s baseline is the most promising next step.
  • The model consumes pre-computed HRV features; a live system would also need a signal-to-feature stage.
  • Research prototype, not a medical or safety-certified system.

How I work

From a question to a model that ships.

Six stages, with evaluation in the middle because it’s the step that can send work back. Each stage below shows what it looked like in the driver-stress project.

Iterates until it holds up on unseen data

1 Define

Frame the prediction task, the users of the output and what “good” means before touching a model.

In the driver-stress project: Binary stress vs. no-stress from HRV features. Precision, recall and F1 are reported for the stress class, and the scope note says plainly that WESAD is lab data, not driving data.

2 Prepare

Validate the schema, clean the data and remove anything that leaks the answer.

In the driver-stress project: Schema validated on load; 196,978 rows → 184,276 after removing exact duplicates. Time (protocol order) and SSSQ (self-reported stress) dropped as leakage; 30 base HRV features kept.

3 Develop

Build the simplest model that can work, as one reproducible pipeline.

In the driver-stress project: A scikit-learn Pipeline (median imputer → Random Forest, 200 trees, balanced classes) with a fixed seed, saved as one joblib artefact so training and inference share preprocessing.

4 Evaluate

Test on people or data the model has never seen, and report the spread, not just the best number.

In the driver-stress project: Leave-one-subject-out CV on 12 subjects (ROC-AUC 0.897 ± 0.114), then one score on 3 held-out subjects (0.940). Per-subject F1 ranges from 0.94 to 0.00, and that range is published.

5 Integrate

Put the model behind a contract that other software can rely on.

In the driver-stress project: FastAPI with /health, /model-info and /predict. Invalid input returns 422 naming the bad fields; a missing model returns 503. A Streamlit dashboard replays held-out recordings through it.

6 Ship

Automate the path from a commit to a running, tested container.

In the driver-stress project: GitHub Actions: install → download data (cached) → train → pytest → Docker build → smoke test of the running API container, on every push and pull request.

Evaluation gate

Back to development until it holds up on unseen data.

The evaluation gate is where the driver-stress model’s per-subject spread (F1 from 0.94 down to 0.00) became visible. The case study reports that spread instead of only the best number.

Quality, built into every step

  • Schema validation on load
  • Leakage columns excluded
  • Subject-independent evaluation
  • pytest: data, model and API
  • Input validation (HTTP 422)
  • Docker build in CI
  • API smoke test on every push
